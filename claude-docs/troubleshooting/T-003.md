# T-003 · 대리 지표로 만든 검증기는 통과 쪽으로 고장 난다

- **증상**: `npm run verify-feeds` 를 통과해 시드에 넣은 한겨레(`https://www.hani.co.kr/rss/`)가 `collect` 실행 후 기사 **0건**이었다. 검증기는 초록불, 파이프라인은 무수확. 나머지 9개 소스는 정상 수집돼서 "특정 소스만 이상하다"로 보였고, 검증기 자체를 의심하기까지 시간이 걸렸다.

- **원인**: 두 겹이다.
  1. 표면 원인 — 한겨레 피드의 `<item>` 에는 날짜 엘리먼트(`pubDate`·`dc:date`)가 **아예 없다**. `_shared/rss.ts` 의 `fromRss` 는 `url`·`title`·`publishedAt` 이 모두 있어야 항목을 살리므로 30건을 전부 버린다.
  2. **진짜 원인 — 검증기가 파이프라인과 다른 것을 재고 있었다.** 옛 스크립트의 판정은 `xml.match(/<item[\s>]/g)` 로 센 **원시 태그 개수 > 0** 이었다. 파이프라인이 실제로 쓰는 `parseFeed` 는 태우지 않는다. 한겨레는 원시 30건이라 이 기준을 여유롭게 통과했다. 계획서에 "죽은 소스를 시드에 넣으면 매일 조용히 실패한다"는 경고가 있었는데, 그 경고를 막으라고 만든 검증기가 바로 그 실패를 통과시켰다.

- **해결**: 정규식 카운트를 버리고 `parseFeed` 를 그대로 import 해 **그 반환 건수로 판정**한다(Node 24 는 `.mjs` 에서 `.ts` 를 그대로 import 한다). 원시 수는 판정에서 빼고 진단용으로만 함께 찍는다 — 둘이 어긋나는 것 자체가 신호이기 때문이다.
  ```javascript
  import { parseFeed } from '../supabase/functions/_shared/rss.ts';
  // ...
  const raw = (xml.match(/<item[\s>]/g)?.length ?? 0) + (xml.match(/<entry[\s>]/g)?.length ?? 0);
  const parsed = parseFeed(xml).length;
  if (parsed === 0) throw new Error(`원시 ${raw}건인데 파싱 0건 (url·title·날짜 중 빠진 항목)`);
  ```
  같은 라이브 피드에서 판정이 실제로 뒤집혔다 — 옛 기준 `raw > 0` 은 통과, 새 기준 `parsed > 0` 은 실패:
  ```
  FAIL 한겨레 — 원시 30건인데 파싱 0건
  OK   BBC World (파싱 31 / 원시 31)
  ```
  한겨레를 뺀 9개 소스로 시드를 다시 만들고 `db reset` + `collect` 를 돌려 **0건짜리 소스가 하나도 없음**(총 324건)을 확인했다.

- **재발방지**: **검증기는 파이프라인이 실제로 쓰는 함수를 태워야 한다. 대리 지표(태그 개수·문자열 존재·HTTP 200)로 판정하면 통과 쪽으로 조용히 고장 난다** — 실패 쪽으로 고장 난 검증기는 시끄러워서 즉시 고치게 되지만, 통과 쪽으로 고장 난 검증기는 초록불을 유지한 채 몇 달이고 산다. 새 검증 스크립트를 쓸 때 자문할 것: **"이 스크립트가 import 하는 것이 프로덕션 코드와 같은 함수인가?"** 아니라면 그것은 검증이 아니라 흉내다. 이 함정은 글로벌 CLAUDE.md 「번들 문자열 검사 — 문자열의 존재는 행위의 증거가 아니다」와 **같은 계열**이다(존재/개수라는 대리 지표를 행위의 증거로 오인). 그쪽은 이미 2개 프로젝트 3건으로 글로벌 승격된 항목이라, 이 건은 그 원칙의 이 레포 실측 사례로 남긴다 — 다음에 또 만나면 원칙 본문에 「검증 스크립트」 사례를 합친다. 무성 실패군이라는 점에서 [T-001](T-001.md)·[T-002](T-002.md)의 형제이기도 하다.
